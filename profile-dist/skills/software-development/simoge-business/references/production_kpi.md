## Production KPI for ANNA (BI narrative)

- Production narrative entry point is `answer_production(tahun, bulan, periode, mode, **wilayah)` in `scripts/ana_kpi.py` — one call returns KPI semantic object + evidence trace + fixed 6-section narrative + 2-sentence asisten short. ANNA never assembles KPI numbers from raw template rows itself.
- Two working entry points: in Hermes desktop chat `execute_code` is fine and cheapest — `sys.path.insert(0, <scripts dir>)` then `from ana_kpi import answer_production` (no shell quoting); in the HUD/intelligence-surface panel arbitrary Python is blocked, so fall back to `terminal` with the absolute profile path. Never `search_files` for it:
  `python3 ~/.hermes/profiles/anna/skills/software-development/simoge-business/scripts/ana_kpi.py tahun=2026 bulan=3 periode=2 mode=asisten`
  Pipes into another interpreter are also blocked — redirect to `/tmp/*.json`, then `read_file`. One call, no discovery flailing.
  `execute_code` wrapping `hermes_tools.terminal` is BLOCKED in INTELLIGENCE SURFACE — call the `terminal` tool directly there; plain `execute_code` Python in desktop chat is not affected.
  Every `terminal` call must set `workdir` = `ANA_WORKDIR` (`.env`) di mesin tsb — without it the shell starts in the wrong cwd and relative paths fail.
- Chart publish butuh env (`ANA_PORT`/`ANA_TOKEN` atau `.ana_token`) atau dia hanya mencetak
  state tanpa menyentuh layar (`visible:false`). Jalankan lewat CLI script, bukan `python3 -c`:
  `PYTHONPATH=<scripts> python3 <scripts>/ana_chart_tool.py show type=bar title=... labels='[...]' datasets='[...]'`
  Jangan laporkan "chart tampil" sebelum panggilannya mengembalikan `visible:true`.
- No-SQL enforcement is structural, not advisory: `ana_simoge_tool` must import `run, T` only and never re-export `q`, and `ana_kpi.py` must import only `call_simoge_tool` — re-verify with an AST import scan after any edit, since a leaked `q` re-opens raw SQL to every ANNA tool-call.
- Coverage gap wording depends on scope: unscoped gap = petak outside RKAP coverage (missing polygon/target); scoped gap = petak outside the wilayah filter. Never report a scoped gap as missing data.
- Never use `rkap_achievement` as a KPI source — it returns a single proof-of-concept row with a wrong `target_periode`. `rkap_map` rows are safe for per-petak polygon colors only — never SUM their `target_periode` for a KPI total: the `JOIN getah_target_ro_nps` fans out multi-row percents before `GROUP BY p.kode_evapot`, distorting the aggregate by thousands of kg. KPI achievement = scalar cumulative RO percent (one small query first) × SUM(`target_rkap`), divided into direct-SUM realisasi. Same rule everywhere: compute any ratio-of-sums scalar in Python first and pass it as a `%s` param — never nest `SUM()` inside `SUM()` (MySQL err 1111) and never aggregate over a fanned-out join.
- Production totals come from SUM over `getah_aktivitas_penerimaan.berat_penerimaan` directly (`produksi_aktiv`, `produksi_year_to_date`). Never route production through a `getah_andil` join — hundreds of penyadap have penerimaan rows but no andil, so the join undercounts. Every realisasi subquery groups by `penerimaan.kode_evapot` directly (`AND kode_evapot IS NOT NULL`).
- "Aktif" has two definitions — state which one every time: aktivitas sadap (`cur>0` in `getah_aktivitas_sadap`, via `idle_petak`/`status_petak_per_wilayah`, both prev = previous period: P2→P1 same month, P1→P2 previous month) vs petak terima getah (`n_petak` from `produksi_aktiv`). Mixing them produces numbers that match no period. For narratives use `status_petak_per_wilayah` aggregates (scoped, partition-guarded) — `idle_petak` is the same definition per-petak, for detail only.
- An empty period means data is not yet entered — report it as unavailable, never as zero production. Guard growth math against a zero/NULL previous period (return null, not infinity). Split the diagnosis instead of merging it: real decline = `n_penerimaan`/`n_petak` falling across consecutive months; input stopped = `aktivitas_agregat` returns `rows=[]` for the month and `data_freshness.tgl_terakhir` is stale. Only the first is a production story. Discriminators that actually separate them: `data_freshness.tgl_terakhir` is `MAX(getah_aktivitas_sadap.tgl_pembaharuan)` (record-side), while setoran-side stop is `MAX(getah_aktivitas_penerimaan.tanggal)` — exposed as `aktivitas_terakhir` on `penyadap_productivity` rows — plus the row count collapse (e.g. 1075 penyadap in a full month vs 111 in a stalled one). `aktivitas_agregat` returning 100 rows proves nothing: it is the `LIMIT`ed penyadap breakdown, not a month-volume signal. A month with 0 `penyadap_productivity` rows has no penerimaan entered — report "belum ada setoran tercatat", never 0 kg.
- Reporting "tahun ini" while the current period is empty: find the latest non-empty `(bulan, periode)` from `produksi_trend.breakdown` first, then call `answer_production` for that period. `answer_production(tahun, bulan_sekarang, 0)` returns only the "belum tersedia" narrative and an empty `production` block, so a naive call reports nothing about the year.
- KPI builder must hard-fail on distortion, never narrate it: `ana_kpi.py` carries an achievement guard (Σ `target_periode` vs Σ `target_rkap` × `target_pct`, `RuntimeError` on >1% drift) and a partition guard (`aktif+idle+bongkor=total`, `RuntimeError` on residue). A guard trip means fix `simoge_db.py`, not adjust the narrative.
- Actual window and target-percent window must cover the same span (both cumulative Jan s/d periode, or both period-only). A period-only actual against a cumulative target (or vice versa) biases achievement silently — the guard above only catches double-count, not span mismatch, so check the `BETWEEN` bounds match the percent helper by construction.
- `petak_simple.json` is dimension + YOY snapshot only (identity, geometry, `meta.generated_at` freshness stamp). It is never a KPI source — every number ANNA narrates comes from a live DB template.
- The server imports the global skill scripts while the ANNA profile resolves its own copy — diff both copies before trusting ANNA-side behavior, and sync them after every `simoge_db.py` edit. After syncing, confirm with `diff -q` rather than assuming the copy landed; a stale profile copy makes ANNA read a skill that no longer matches the code it is running against.
- `server.py` imports the skill scripts once and caches them in `sys.modules` — restart the dashboard server after every `simoge_db.py` edit, otherwise `/api/simoge/*` keeps serving the old templates and fixes until restart. Restart via `terminal(background=true)` — never `nohup ... &` in a foreground call (the runner rejects shell-level background wrappers); then verify readiness in a separate call (`/api/token-status` + token-gated `/api/map/queue`).
- After editing `simoge_db.py`, execute every touched template once with real params — alias mismatches between a subquery SELECT and its outer reference only surface at query time.
- Delete a guard constant when the behavior it describes changes — an unenforced denylist that contradicts live scoped code misleads future sessions more than no constant at all.
- A duplicate `server.py` process is a red herring, not a failure: a second copy started from a different cwd (a symlinked path) dies or binds nothing while the live one still holds the port. Confirm with `ss -ltnp | grep <port>` plus an unchanged boot id from `/api/token-status` BEFORE restarting — an unchanged boot id means the live server was never touched. Kill by PID (`pgrep -f "^python3 server.py" | head -1`), never `pkill -f`, which matches the calling shell and kills the tool call itself.
- `produksi_per_wilayah` filtered by `bulan` returns CUMULATIVE Jan..bulan (YTD) per BKPH, not that month's production — the totals rise monotonically. For monthly per-BKPH, subtract consecutive months' breakdowns and sanity-check that the month deltas sum to `produksi_trend` for the same period; never quote the cumulative value as "produksi bulan X". Same shape check applies to any `_per_wilayah` KPI.
- Tool-call shape: `call_simoge_packet` is for row-shaped intents (`produksi_trend`, `*_per_wilayah` breakdown, `aktivitas_agregat`) — on single-row aggregate templates it collapses the payload to `{"rows": 1}` (or a lone count like `{"n_penyadap": 46}`) and silently drops the measured fields. When you need a scalar or one-row result (`data_freshness`, `rencana_aktivitas`, `produksi_aktiv`, `status_petak_per_wilayah` rows), call `call_simoge_tool(name, params)` and read `rows` — it returns `{ok, columns, rows, row_count, sql}`. If a KPI looks suspiciously empty, that is the first thing to check.
- `execute_code` stdout over roughly 1 KB comes back elided, so a single big `print(json.dumps(...))` can hide the whole answer. Write the payload to `$SCRATCH/<topic>.json`, then print one field per call (`print(json.dumps(k.get("achievement"), ...)[:700])`) or short slices of the file. Keep each print under ~900 chars; collect in one call, read in several small ones.
- Render the panel with `show_dashboard(title=..., kpis=[{label,value}...], charts=[{type,title,labels,datasets}...], narration=..., evidence=[...], meta={...})` and report the result only after `visible` is `True`. KPI cards carry ton + percent + gap; charts carry the per-BKPH or per-period comparison — one chart is never enough for a why/how answer.
